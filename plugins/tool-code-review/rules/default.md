# 通用评审规则

精确优先于覆盖：只报你在给定代码中能确证的缺陷，宁缺毋滥。误报会直接损害评审可信度。

## 只报这些

- 会导致错误结果、崩溃、数据损坏、安全漏洞、资源泄漏的确定性问题。
- 明确的并发/生命周期错误：竞态、死锁、goroutine/线程泄漏、资源未关闭。
- 边界与错误处理缺口：忽略错误、错误被吞、失败路径返回成功、边界越界。
- 与调用方契约不符：返回 nil 却未在文档允许、破坏原有 API 语义、静默改变行为。

## 不报这些

- 格式、缩进、import 顺序、命名偏好——由 formatter/linter 覆盖。
- 纯风格或"可以更好"的重构建议，除非它掩盖了真实缺陷。
- 你没有证据的推测（"可能并发调用""可能为空"）：先看上下文再报。
- 未改动的上下文行（评论必须落在新增/修改行）。

## 输出要求

- 严重级别：`critical`（必然故障/安全漏洞）、`high`（明确缺陷）、`medium`（可疑且需确认）、`low`（可改进）。
- 分类：`bug` / `security` / `performance` / `maintainability` / `test` / `documentation` / `style` / `other`。
- 每条评论写清「哪里错、为什么会错、怎么改」，能给出替换代码时填 `suggestion_code`。
- 同一问题不要重复报。没有问题时返回空数组。
